# ARDOS Guardian G2

This repository is the **G2 development line**. It is private and invite-only.
It shares its history with the public G1 repository up to the `1.0.0` release
and diverges from there.

| | G1 | G2 |
| --- | --- | --- |
| Repository | `bubakbubak500/ARDOS-Guardian` | `bubakbubak500/ARDOS-Guardian-G2` |
| Visibility | public | private, invite-only |
| Common ancestor | `Release 1.0.0` (`65e09cb`) | same |
| Version series | `1.x` | `2.x` |

## What G2 is for

G2 exists to develop the **Guardian G2 soundcard modem**: a payload modem Guardian
owns entirely, with no VARA behind it. Guardian generates the waveform, puts it
on the air through the soundcard and keys the radio itself. The proven OFDM PHY
remains the default; release 2.3.0 adds separately selectable SC-HS, SC-FTN and
SEFDM physical-layer modules without changing the established control frames.

That is the reason for a private line. The modem is experimental, the occupied RF
bandwidth is still to be measured on real radios, and it will change shape as
those measurements come in — none of which belongs in a public release that people
are running for emergency traffic. Everything G1 does, G2 still does: the ARDOS
control plane, routing, the mail layer and VARA P2P are unchanged, and VARA remains
the default transport.

See [docs/G2_WAVEFORM_LAB_2.3.0.md](docs/G2_WAVEFORM_LAB_2.3.0.md) for the
2.3.0 waveform comparison and radio procedure, and
[docs/ofdm-vhf.md](docs/ofdm-vhf.md) for what the original OFDM modem is, what it has
measured and what it deliberately does not do yet, and
[docs/OFDM_AIR_TEST.md](docs/OFDM_AIR_TEST.md) for the on-air procedure as four
numbered tests, with a Czech version at
[docs/OFDM_AIR_TEST.cs.md](docs/OFDM_AIR_TEST.cs.md). [docs/OFDM_VHF_PLAN.md](docs/OFDM_VHF_PLAN.md) keeps the original
plan alongside a record of where the implementation had to depart from it.

Version numbers cannot be confused between the lines: G1 stays on `1.x`, G2 runs
`2.x`. CI checks a tag against `guardian.__version__`, so a tag pushed to the
wrong remote fails rather than publishing.

## One working copy, two repositories

Both lines are driven from a single local clone at
`C:\Users\ok7ps\Documents\Guardian`. There is one `.git`, one history, and one
working directory; the branch you are on decides which repository you are
talking to.

```
branch main → remote origin → ARDOS-Guardian     (public)
branch g2   → remote g2     → ARDOS-Guardian-G2  (private, lands as "main" there)
```

```powershell
git switch g2      # work on G2
git push           # goes to the private repository only

git switch main    # work on G1
git push           # goes to the public repository only
```

### Why a plain `git push` cannot cross the boundary

The clone is configured so that the wrong remote is not reachable by accident:

```
branch.main.pushRemote  = origin
branch.g2.pushRemote    = g2
branch.codex/modernization.pushRemote = origin
remote.g2.push          = refs/heads/g2:refs/heads/main
```

The pinned refspec means the private remote accepts **only** the `g2` branch.
Running `git push g2` while standing on `main` does not publish the public
branch into G2, and no branch other than `g2` is pushed to G2 implicitly.

Nothing committed on `g2` should ever reach the public repository. Check the
current branch before pushing.

### Moving work between the lines

The shared history makes this ordinary:

```powershell
git switch g2
git cherry-pick <sha-from-main>    # take a G1 fix into G2

git switch main
git cherry-pick <sha-from-g2>      # publish a G2 change, when it is meant to be public
```

## Builds: local only

GitHub Actions is **disabled** for this repository. Private repositories draw
on the free Actions quota and `windows-latest` bills at a 2x multiplier, so for
now G2 is built on the workstation:

```powershell
.\build.ps1
.\build_installer.ps1 -Compiler "<path-to-ISCC.exe>" -ReleaseBaseUrl "<url>"
```

The workflow files under `.github/workflows/` are still present and unchanged
from G1, so nothing is lost. Re-enabling is a repository setting, not a code
change:

```powershell
gh api -X PUT repos/bubakbubak500/ARDOS-Guardian-G2/actions/permissions -F enabled=true
```

### The update channel is G2's own

Both halves of the updater point at the G2 repository, and they have to:

- `guardian/updates.py` `DEFAULT_MANIFEST_URL` — where an installed G2 asks
  whether an update exists.
- `build_installer.ps1 -ReleaseBaseUrl` and `release.yml` — what the manifest a
  release publishes says to download.

G1's manifest is harmless today, because it advertises 1.0.0 and nothing older
than the installed version is ever offered. The hazard is the first G1 release
numbered above the installed G2 version: the station would download and run a
*G1* installer, which has a different AppId and a different directory, so the
operator would end up with G1 installed, G2 untouched, having pressed a button
that said "update". Never point a G2 build at the G1 channel.

Because the G2 repository is private, an unauthenticated check answers 404 and
the updater reports no update available. That is correct until a G2 release is
actually published, and it can never offer a G1 build.

## Installed side by side with G1

G2 is a separate product on the machine, not an upgrade of the public build. The
operator can keep G1 installed and working while running G2 — one at a time,
since both talk to the same radio and the same VARA ports, but both installed.

| | G1 | G2 |
| --- | --- | --- |
| Inno Setup `AppId` | `{CF48D1B9-ABC0-4DC5-A97E-00334B9DF040}` | `{D9090316-F68C-4DAE-AF02-B433658A8F15}` |
| Displayed name | Guardian | Guardian G2 |
| Install directory | `%LOCALAPPDATA%\Programs\Guardian` | `%LOCALAPPDATA%\Programs\Guardian-G2` |
| Executable | `Guardian.exe` | `Guardian-G2.exe` |
| Start-menu group / shortcut | Guardian | Guardian G2 |
| `AppUserModelID` | `OK7PS.ARDOSGuardian` | `OK7PS.ARDOSGuardian.G2` |
| Setup file | `Guardian-<ver>-setup-win-x64.exe` | `Guardian-G2-<ver>-setup-win-x64.exe` |
| Station data | `%APPDATA%\Guardian` | `%APPDATA%\Guardian-G2` |

A fresh `AppId` is what makes the two uninstall entries independent: with a
shared one, installing G2 would be recorded as an upgrade of G1 and removing
either would remove both. The distinct exe name is not cosmetic either — it is
what tells the two apart in Task Manager, in taskbar pinning and in the
`AppUserModelID` grouping.

### Why the data directory has to be split

`config_dir()` (`guardian/config.py`) returns `%APPDATA%\Guardian-G2`, with
`~/.guardian-g2` as the non-Windows fallback. Everything per-station moves with
it: `config.json`, `routes.json`, `topology.json`, the mail store, map tiles,
the generated icon and glyph caches, downloaded Hamlib.

Sharing one directory would not merely be untidy, it would lose settings.
`StationConfig.load()` drops keys it does not recognise and `save()` writes the
whole dataclass back, so a G1 build — which knows nothing about the G2 payload
modem — would silently strip every G2-only setting from `config.json` the first
time it was started. The split makes that impossible.

### One-time seeding from G1

So the operator does not have to enter the station twice, the first run copies
`%APPDATA%\Guardian\config.json` into the G2 directory if G2 has no
`config.json` of its own. It happens once and it only ever copies: G2 never
writes back into the G1 directory, and once G2 has its own file, G1's is not
read again.

The source is always the sibling of the directory being written, under the same
root, so redirecting `APPDATA` (which `tests/conftest.py` does at import time)
isolates the seeding completely — a test run cannot reach a real profile.

Hamlib is external software, so `find_executable()` still looks in a G1 copy
under `%APPDATA%\Guardian\hamlib` after checking G2's own directory.

## Tags

Tags live in the shared local clone and are not pushed by `git push`. Always
push a tag to one named remote deliberately:

```powershell
git push g2 v1.1.0        # G2 release tag
git push origin v1.0.1    # G1 release tag
```

Once the two lines carry different features, they need version numbers that
cannot be confused with each other — CI checks the tag against
`guardian.__version__`.
